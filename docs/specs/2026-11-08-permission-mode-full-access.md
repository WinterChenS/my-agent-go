# 权限模式：询问 / 允许完全访问（2026-11-08）

用户提供的原型：编辑框下方一个"⚠ 允许完全访问 ^"的选择器，展开后是一张卡片——

> 当前权限为允许完全访问，请注意数据安全，建议执行可信任的任务。
>
> 允许完全访问　[开关]

即：**开启后不再逐次弹审批**。这属于产品能力，不是"把审批 TTL 调长"，必须当成一个显式的权限档位对待。

## 决策

1. **两个档位**，存 `Settings.PermissionMode`：
   - `"ask"`（默认）——每次写动作/命令都要审批（当前行为）
   - `"full_access"`——同一会话内不再询问，但仍**逐条记录**（见第 3 条）
2. **在 run 受理时钉住**。权限档位进入 `ExecutionBinding` 快照：运行中切换开关只影响下一个 run。
   理由：中途改变判定会让同一条 run 的前后步骤适用不同规则，回放/复现时无法解释。
3. **跳过审批 ≠ 不留痕**。`full_access` 下每次调用在事件流里记 `policy.auto_allowed`（工具名、参数摘要、
   run/session），诊断页可查。审批卡不出现，但"发生了什么"必须能追溯。
4. **无人值守 run 拒绝 `full_access`**：定时任务、后台续跑一律按 `"ask"` 处理，缺人工答复则按既有规则失败
   （C09 已有 60s → failed 且无副作用的口径）。理由：定时任务不该因为用户白天开过一次完全访问就永久免审。
5. **可视且可逆**：开启后页脚常驻"⚠ 允许完全访问"，点击即可切回；聊天页顶部同时显示警示条
   （文案用原型原句，不自己发明）。关闭窗口不改变设置（持久化）。
6. **不越过平台硬边界**：文件系统仍限制在工作区（`workspace`）；`full_access` 只免除**人工审批**，
   不把 `unrestricted` 塞进权限。要真正放开范围，仍需在设置里显式改文件系统档位——两个开关不要合并。

## 验收（agent-desktop 真机）

| 步骤 | 断言 |
|---|---|
| 默认启动 | 页脚显示"询问"，写动作弹审批卡 |
| 打开开关 | 页脚变"⚠ 允许完全访问"，出现警示条，文案与原型一致 |
| 再次执行同一命令 | **不弹审批卡**，命令真的执行；事件流里出现 `policy.auto_allowed` |
| 关闭开关 | 恢复弹卡；下一条命令重新需要审批 |
| 运行中切换 | 当前 run 继续按旧档位；新 run 用新档位（事件里能看到两个 binding） |
| 定时任务 | 即便 `full_access` 开启，无人值守 run 仍按 ask 处理并按时失败，无副作用 |
| 诊断页 | 能查到被自动放行的调用记录 |

## 归属

排在第 ①（会话页复刻 + 对话跑通）之后、第 ②（agent 适配层）之前，因为它是**审批链路**的一部分，
而 ① 的卡片验收正是这条链路。
