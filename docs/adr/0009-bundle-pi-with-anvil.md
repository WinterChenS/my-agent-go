# ADR 0009：Anvil 安装包内置 Pi，运行时只用包内版本

- 日期：2026-11-27
- 状态：已采纳
- 取代：旧“宿主 Pi + 应用内一键 `npm install -g`”交付方式（F06 / ADR 0002 的残留约定）
- 影响任务：PIB01（打包）、PIB02（运行入口与数据根）、PIB03（界面状态与安装/升级/卸载验收）

## 背景

到今天为止，Anvil 把 Pi 当成**宿主依赖**：应用启动后扫描 `PATH` 和已知 npm 前缀，找到一个外部
`pi` 就当运行时用；找不到时，设置页提供“一键安装”，实际执行
`npm install --global --prefix <prefix> @earendil-works/pi-coding-agent`。

这条路径有四个已知缺口：

1. **首次安装不等于可用。** 干净机器上没有 Node、没有 npm、没有 Pi，安装完 Anvil 打开只是一个
   “未安装运行时”的空壳，还要联网再走一次 npm 安装。断网机器永远走不过去。
2. **一次安装可以改变另一台进程的行为。** 应用写的是共享前缀（Windows
   `%LOCALAPPDATA%\pi-node\current`），一个全局 npm 前缀的改动会影响用户系统终端里的 `pi`；
   反过来，用户升级/降级外部 `pi` 会悄悄改变 Anvil 的行为。
3. **版本不由我们决定。** 兼容范围是 `>=1.5.0 <2.0.0`，但实际跑的是机器上碰巧装的那一个；
   回归只能靠用户撞见。
4. **数据根落在 Pi 的默认位置。** `PI_CODING_AGENT_DIR` 未设置时是 `~/.pi/agent`，Anvil 的
   catalog、Skill、会话各按一套自己的规则推导，和 Pi 的实际读写位置存在漂移面。

## 决策

1. **交付方式改为应用内置。** Tauri 安装资源携带官方 npm 包
   `@earendil-works/pi-coding-agent`（首轮锁定 `1.6.0`）和**同版本私有 Node 24.16.0**
   （按目标架构准备），落在安装资源的 `runtime/pi/`。安装或首启阶段**不执行 npm**。
2. **运行时只用包内 Pi。** 正式桌面入口的探测、聊天 RPC、模型/MCP 同步、OAuth helper、定时会话
   和现有子代理扩展都从同一份包内启动配置出发（`BundledPi`），不再接受外部 `pi` 作为执行入口。
   外部 Pi 仍可在系统终端独立使用；Anvil 不修改、不升级、不删除它。
3. **数据根跟随 Anvil。** 包内 CLI 的子进程环境显式设置 `PI_CODING_AGENT_DIR = HostConfig.data_dir`
   （默认 `~/.anvil`），用户级 Skill 根为 `<data_dir>/skill/`。显式 `ANVIL_DATA_DIR` 的宿主校验
   与 Windows D 盘约定不变。
4. **升级由 Anvil 更新器负责。** Pi 检查更新复用 Anvil 自己的签名更新链路：新版本随安装包一起
   到来，Pi 版本跟随包内 `manifest.json`。旧的外部安装记录按既有失效流程处理，但保留
   `runtime_id = "pi"`、Agent 引用与原生会话 ID；旧安装按钮和自动 launcher 修复**不得**再绕回
   `npm install -g`。
5. **卸载即移除安装资源。** 走当前平台标准卸载入口，移除私有 Node、Pi 代码和包内插件资源；
   默认保留 `~/.anvil` 的用户数据，保留外部 Pi 及其配置。
6. **打包失败即停止发布。** 目标架构不对的 Node、缺失的 Pi CLI、缺失的 `examples/extensions/subagent`
   资源都让打包命令非零退出，该平台的安装包不上传，避免发出一个“能装但跑不了”的包。
7. **验收以本次安装包为准。** 新版真实验收使用实际打包的 NSIS / MSI 安装产物、其落盘资源与
   实际进程；此前的宿主 Pi 验收证据（`docs/evidence/pi-compatibility.md` 等）作为历史记录保留，
   不再代表当前交付方式。

## 后果

- 安装包体积增加（私有 Node + Pi 生产依赖），换来的是断网可装、行为可控、版本可复现。
- 构建流程多一步“准备包内运行时”，必须在打包安装包之前完成并通过校验；`cargo test` 不依赖它
  （用注入的测试路径），所以干净工作树仍能跑 Rust 测试。
- 本机已装的外部 Pi 1.6.0 与锁定的包内版本一致，因此 PIB02 的切换不引入版本行为差异；差异
  只出现在交付方式上。
- `PI_CODING_AGENT_DIR` 迁到 `~/.anvil` 后，旧用户 `~/.pi/agent`、`~/.pi/skills` 的配置和 Skill
  需要显式导入；凭证（OAuth / API Key）默认由用户在现有登录界面重新配置，不做静默复制。
- 平台发布矩阵不变（ADR 0005 / ADR 0008）。内置资源必须按**目标架构**准备，包含 macOS Intel
  交叉构建。

## 与既有决定的冲突

| 既有约定 | 冲突点 | 本 ADR 的处理 |
|---|---|---|
| ADR 0002（推迟 F06 Pi 安装器） | 当时把安装外包给外部 npm | 由安装包承担；F06 的一键安装降级为兼容外壳，Pi 分支返回“已内置” |
| ADR 0007（Rust + Tauri 重建） | 无冲突 | 继续用 Rust/Tauri 交付，只是多了安装资源 |
| 旧里程碑的“本机 Pi 真实用例”取证口径 | 旧口径要求使用本机已装 Pi | 改为使用**包内** Pi 取证；本机 Pi 仍可用于对照，但不再是执行入口 |

## 为什么不选其它方案

| 方案 | 不选的原因 |
|---|---|
| 继续用宿主 Pi + 一键 npm 安装 | 断网装不了、版本不可控、会改用户全局环境；用户明确要求内置 |
| 把 Pi 编译成单文件二进制塞进基础包 | 换承载方式属于 ADR 级别改动，且与 Pi 官方发布形态、插件示例资源路径都不一致 |
| 内置 npm 并在首启时联网安装 Pi | 首启依赖网络，用户要的是离线可用；且首启失败会留下半装状态 |
| 只内置 Pi 不内置 Node | 目标机器可能没有 Node，或版本低于 Pi 要求（`>=22.19.0`），等于把缺口留给用户 |
| 静默复制旧 `~/.pi` 的凭证到新数据根 | 违反最小惊讶与凭证处置约定；导入必须由用户确认 |
